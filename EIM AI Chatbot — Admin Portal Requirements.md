## 3. Roles and access control

A two-tier model is agreed: EIMO and policy owners can act, while MBO and MDO stakeholders can only view metrics. Matt summarized it and all participants agreed. It is built from multiple AD groups, whereas today one AD group opens the whole portal.

| Capability | EIMO submitter | EIMO reviewer or approver (second LOD) | MBO / MDO viewer | Src |
| --- | --- | --- | --- | --- |
| View KPI dashboard | Yes | Yes | Yes (same view as each other) | M1, M2 |
| View MPT and audit stats | Yes | Yes | Yes | M2 |
| Submit feedback on a response | Yes | Yes | **No** | M2 |
| Delete a single piece of feedback | Open | Open | No (EIMO only) | M2 |
| Choose between conflicting feedback | No | Yes | No | M2 |
| Upload and clean up KB documents | Yes | No | **No** | M2 |
| Approve and publish KB documents | No | Yes | No | M2 |
| Add or edit golden Q&A | Yes | Open | No | M2 |
| Run golden Q&A and see results | Open | Open | Runs quarterly; where it runs is open | M2 |
| Export CSV of chat data | Open | Open | Open | M2 |

**Decided:** MBO and MDO do not need to be segregated from each other; they simply all need access. Feedback and KB editing stay exclusively with EIMO and policy owners.

**Still open:** whether reviewer and approver are separate people or one group, which AD groups map to each column, and who may export raw data. Nichola takes the role decisions to Kate before they are final.

**Why the split matters.** Feedback reaches the model within minutes, so an unreviewed or wrong correction can degrade answers quickly. Segregation of duties gives each change a second set of eyes.

**Details noted for build**

- Feedback is tagged with the submitter's name from their login, so conflicting feedback can be traced to the policy owners who gave it.
- Each chatbot will have its own admin URL for now. A single portal across 3 to 6 future chatbots is deferred.
- Sanjiv's team must see the dashboard for audit demonstration; the audit trail includes his confirmation emails to Claire (see section 7).

## 5. Feedback

Admins review individual conversations, grade the AI's answer and write a correction that reaches the model within minutes. Conflicts between policy owners go to a second line of defense.

### Verdict categories

| Verdict | Meaning in M2 | Goes to the LLM? | Src |
| --- | --- | --- | --- |
| Correct | No further action needed | No | M2 |
| Incomplete | Likely a gap in the knowledge base | Yes, with a corrected answer | M2 |
| Has Error | Slight inaccuracies or rewording needed. The code spells it "Has Errors" | Yes, with a corrected answer | M2, Code |
| Unclear | Response is too confusing | Yes, with a corrected answer | M2 |

**Open:** Satish noted "Has Error" and "Unclear" could merge, leaving three categories. Not decided. A merge changes the verdict list and its validation in the backend.

### Workflow

&#91;embedded content: feedback workflow · 2 decisions, 1 revert path\]

A "Correct" verdict ends the flow. Anything else needs a corrected answer, becomes a numbered version tagged with the submitter's name, and is applied within minutes unless two versions conflict, in which case a second LOD chooses.

### Details wanted

| ID | Requirement | Detail | Src |
| --- | --- | --- | --- |
| FB1 | Review a conversation | Admin opens one conversation (question, answer, cited sources, user thumbs rating and comment) and categorizes response quality | M2, Code |
| FB2 | Edit the question | The original user question is editable before submitting | Code |
| FB3 | Corrected answer | Required, at least 20 characters | Code |
| FB4 | Near real-time effect | Added to the LLM's context within a couple of minutes at most, unless the LLM is down. Not synced weekly or monthly | M2 |
| FB5 | Submitter tag | Every item carries the submitter's name from their login. The backend payload today accepts a client-supplied created\_by; deriving it server-side from the session would make the tag trustworthy | M2, Code, Proposed |
| FB6 | Selective delete | Delete individual feedback items. Only "delete all" exists today | M2 (decision) |
| FB7 | Revert | Remove feedback that inadvertently degraded the LLM | M2 |
| FB8 | Second set of eyes | A reviewer or approver verifies accuracy before feedback becomes permanent | M2 |
| FB9 | Versioning | Each submission gets a version number; one version can be accepted | Code |
| FB10 | Conflict flag | A message with more than one version is flagged; resolved and unresolved lists are kept | Code |
| FB11 | Triage list | Sessions across all users, filterable by user, with response count, thumbs up, thumbs down, unrated, feedback count and unresolved conflicts | Code |
| FB12 | Two kinds of rating | End-user thumbs and admin verdicts are separate and both reported. Thumbs data is an MPT requirement | M2, Code |

### Conflict scenarios

| Scenario | Expected behavior | Who decides | Src |
| --- | --- | --- | --- |
| Two policy owners give different corrections for the same answer | Both are kept as versions, the conflict is flagged and both names are visible | Second LOD selects which to accept | M2, Code |
| An accepted correction makes answers worse | Delete that single item instead of using "delete all" | Reviewer or approver | M2 |
| Feedback is submitted while the LLM is down | Application is delayed until the LLM is back | Automatic | M2 |
| One policy owner submits one correction, no conflict | Applied within minutes | Automatic, see open question | M2 |

**Open question that affects the design:** M2 says feedback is applied near real time, and also that a second set of eyes should check it before it becomes permanent. Either it goes live on save and is reviewed afterwards with revert as the safety net, or it waits for approval and the delay grows from minutes to however long review takes. EIMO should choose. \[Proposed\]

## 6. Knowledge base management

KB changes follow a submitter, reviewer, approver model, so no one person can publish a document alone. This was agreed in M2 after Matt and Nichola raised it, and it applies to feedback too.

| Step | Who | What happens | Src |
| --- | --- | --- | --- |
| 1. Upload | Submitter (EIMO, first LOD) | Uploads the policy document | M2 |
| 2. Clean up | Same submitter | Fixes extraction and formatting issues in the extracted text | M2 |
| 3. Approve and publish | Second LOD | Holds approval and publish authority | M2 |

### Lifecycle

The four statuses are the ones the knowledge base schema already uses. Only an approved version is active, and an older active version becomes superseded.
